# 写好开源项目 README 的规则

> **文档用途**：供另一台机器上的 AI（README 写作 skill 的更新者）学习。重点是**一份好的 README 应该长什么样、应该遵守哪些规则、应该做哪些事**。
>
> **来源**：从一次真实开源项目（macOS 菜单栏 app "Timap"）的反复打磨提炼。每条规则都附"反例 → 正例"对照，便于 skill 识别坏写法。
>
> **形式约定**：第一章给标准结构（一份好 README 的骨架），第二章给每一节的具体规则，第三章给跨章节的通用原则，第四章给发布前的最终检查。流程性内容（多轮 sub-agent 评审、Timap 案例研究）放在附录。

---

## 一、一份好 README 应该长什么样：标准结构

按从上到下顺序，**所有 README 都应该有的部分**：

1. **标题** + 语言切换链接（如果双语）+ badges
2. **Tagline**（1-2 行）— 必须有画面感，不能是抽象的产品定义
3. **Hero 截图**（1 张大图，居中）— 单图卖货
4. **"能干什么 / What it does"** — 3-4 条 bullet，最多
5. **安装**
   - 主推方法（最常见路径）
   - 安装受阻处理（按可靠性排序，最稳的方法在前）
   - 备选方法（如从源码构建）
   - 装好之后找不到入口的兜底（特别是菜单栏 app / 后台服务）
6. **用法 / 快速上手**
   - 截图为主，文字最少
   - 用"动作 → 效果"格式
7. **License + Copyright**

**有作者明确意愿才出现**（默认不要写）：
- "Contributing / 贡献者" 段
- 详细架构说明
- 测试 / 构建命令清单
- "PRs welcome" 等贡献邀请

**判定**：作者期不期望别人来改自己代码？默认假设"不期望"，README 写得简洁、不主动邀请贡献。如果作者明确说"欢迎贡献"，再加上述段落。

## 二、每个部分的具体写作规则

### 2.1 Tagline

**规则 1：必须有画面感，禁止"产品经理腔"。**

读者扫一眼大脑里出现的应该是**画面**，不是产品定义。

> ❌ "跨时区协作的 macOS 菜单栏小工具。把'今天什么时候能开会'从数学题压成一张图。"
>
> 问题：抽象比喻（"压成一张图"、"数学题"）需要读者翻译；"跨时区协作"是分类词，不是画面。

> ✅ "一秒看见每位同事此刻几点。菜单栏点一下，世界地图上你的同事正在睡觉、吃午饭还是开会，一目了然。"
>
> 为什么好：用感官词（看见、睡觉、吃午饭、开会、点）+ 具体画面（世界地图）+ 时间锚点（一秒、此刻）

**规则 2：用第二人称"你"，不要用第一人称作者自述。**

> ❌ "我在一家国际公司工作，团队散在三大洲……"（第一人称作者自述）
>
> ✅ "菜单栏点一下，**你的**同事正在睡觉、吃午饭还是开会……"（第二人称代入）

**规则 3：禁止把不相关的两句话糅进一行。**

> ❌ "写给每天打开 Slack 前要先做三道时区算术题的人。SwiftUI · Swift Package Manager · macOS 13+。"
>
> 问题：前半句是情感钩子（给目标读者画像），后半句是技术栈（给贡献者）。两个目的、两个读者，不该挤在一句话里。
>
> ✅ 拆开：技术栈放进 badges，情感钩子用其他方式表达 OR 删掉（badges 已经传达了）。

**判定测试**：把 tagline 读出声，闭眼一秒，**脑子里出现的是抽象定义还是具体画面**？是定义就重写。

### 2.2 Hero 截图

Hero 截图不是装饰，是**单图卖货**。

**规则 1：截图要捕捉"产品最值得展示的那一秒钟"，不是任意一个状态。**

如果产品的关键价值是某个动态/算法功能（比如自动找最佳会议时段），hero 截图必须**视觉化**地展示它工作的瞬间。

**规则 2：演示数据要展示价值，不能是开发者乱填的测试数据。**

- ❌ Mira Chen / Jordan Park / Sam Okafor + Seattle / Boston / Chicago — 听起来像谁随手编的，地理上又集中在美国，没有"国际团队"画面
- ✅ Daniel Cole（伦敦）+ Maya Patel（纽约）+ 北京（家城）— 听起来是真实姓名 + 地理跨欧美亚 + 至少 3 个时区差异

**规则 3：画面要有"差异 + 故事"。**

如果所有元素状态一致（全在工作 / 全在睡），没张力。差异大但分布无逻辑，又显得乱。**理想是 3-4 个元素覆盖 2-3 种状态**，让读者看一眼就知道"啊原来这个产品是干这个的"。

**规则 4：算法功能必须视觉显著。**

如果产品有"找最佳重叠时段"、"自动推荐"、"AI 分类"等算法功能，hero 截图里相关 UI 元素必须显眼：颜色突出、位置居中、面积足够大。

举具体例子：Timap 的 hero 早期版本里"全员重叠时段"的绿色 band 又细又靠右上角，"用户一眼都看不出来"。后来调整 demo 团队的工作时长让 band 加宽到 4 小时居中显示才足够显眼。

**规则 5：数量克制。**

不要为了"看起来产品功能丰富"在 hero 里塞 6 个城市卡 / 6 行数据。3-4 个就够。多了反而让读者扫不过来 + 产生"这个工具好复杂"的反感。

**规则 6：不要用真实姓名 / 真实公司数据。**

哪怕产品场景就是公司团队，hero 也要用合成的姓名（避免泄露隐私 + 让公开仓库不会让作者尴尬）。

**规则 7：本地化考量。**

如果产品定位是中文 / 亚洲用户，hero 里的"主角"（home 城市、第一人称视角）最好是北京 / 上海 / 东京 等，让目标读者一眼带入"这是我"。

### 2.3 "能干什么 / What it does" 段

**规则 1：只放 3-4 条 bullet，超过这个数字砍掉最弱的。**

读者第一屏的扫描预算很有限。再多就开始失去注意力。

**规则 2：不要堆砌"基线特征"。**

只放**目标读者可能不预期、能让他们说"哇这个还能这样"的那些东西**。把"该品类应有"的基础功能塞进 features 段，反而显得没东西可说。

> ❌ "🌐 中英双语 + IANA 时区"（在菜单栏时区工具品类里是基础预期）
> ❌ "🏠 安静住在菜单栏 — 没有 Dock 图标"（菜单栏 app 的本质特征）
>
> 这俩相当于外卖 app 把"可以下单 / 可以付款"列进卖点 — 用户看完反而觉得"就这？"

**规则 3：每条 bullet 用"用户痛点 → 用户动作 → 用户得到的东西"结构，禁止技术语言写卖点。**

> ❌ "✨ 自动找全员重叠窗口 — 把所有同事的工作时段以 30 分钟为步进求交集，按重叠人数和连续长度排序"
>
> 问题：开发者文档腔。"求交集" "按 X 排序" 是实现细节，不是用户视角。

> ✅ "✨ 自动找大家都能开会的时段 — 把每个城市的工作时段对齐起来求重叠，按好用度排序。点左上角时间数字，一键跳到下一个推荐时段。"

注意：精确度信号（"30 分钟为步进 / IANA / DST"）可以保留，**但放在用户价值之后作为 supporting detail**，不要打头。

**规则 4：bullet 标题（emoji + 主标题）必须是用户视角的"我能得到什么"，不是技术名词。**

> ❌ "🌍 全队定位实时上图"（"全队定位"是技术名词）
> ✅ "🌍 同事所在城市，地图上一目了然"（用户视角描述）

> ❌ "🎚 时间轴可拖动"（在描述控件功能）
> ✅ "🎚 时间轴随手拖" + 紧跟一句具体场景（"下周二北京晚 10 点谁还醒着？拖过去答案在卡上"）

### 2.4 安装段

这是**最容易翻车的段**，因为作者在自己机器上从不会真的执行这些指令。

**规则 1：每个版本发布都同步更新下载链接里的版本号。**

`Timap-0.1.3.dmg` / `pip install xx==1.2.0` 这种具体引用必须随发版同步改。

**规则 2：平台 / 版本拦截行为必须在最新目标系统上实测。**

不要照搬旧的 README 模板。例如 macOS 14 推荐的"右键 → 打开"在 macOS 15 / 26 上根本不显示"打开"按钮；macOS 15+ 对 ad-hoc 签名 app 直接报"已损坏"对话框（不是更温和的"无法验证开发者"）。

**规则 3：多种处理方式都给出来，但要明确每种的失效场景，主推最稳的那个。**

> ❌ "方法 1：系统设置 → 仍要打开（推荐）" + "方法 2：终端命令（备选）"
>
> 问题：这是 macOS 14 习惯，到 15+ 主推方法不通。

> ✅ "方法 1：终端一行命令（推荐 · 任何 macOS 都管用）" + "方法 2：系统设置 → 仍要打开（不一定有这个按钮）"，并在方法 2 上明标"macOS 15 / 26 上看到'已损坏'对话框时此按钮通常不出现"。

**让用户知道每种方法的限制**比表面上"提供多种方法"更重要。

**规则 4：用户可能踩的"非主流"坑要主动写进去。**

作者认知里的"标准入口"用户可能根本看不到 / 用不了。两个 Timap 实战例子：

1. **菜单栏 app 在带刘海的 MacBook 上，图标可能藏在刘海后面**。README 必须提"找不到图标？" 的兜底入口（双击 .app / Spotlight 启动）+ 推荐 Hidden Bar / Ice 等长期解决工具。
2. **GitHub Releases 页面的 "Assets" 标签很多用户不认识**。README 要明说"在最新版本下方的 **Assets** 区域里找到并点击 `xxx-1.0.0.dmg`"，不要默认用户懂 GitHub 约定。

**规则 5：不要用 `<details>` 折叠关键安装步骤。**

折叠后用户会以为"标题就是全部"，错过下面的关键步骤。安装受阻是用户最焦虑的时刻，**所有步骤直接 inline 展开**，不要让用户多点击一次才看到。

### 2.5 用法 / 快速上手段

**规则 1：每一步用一句话路径 + 截图。文字不要复读截图里的内容。**

> ❌ "第一次打开是欢迎页：logo 装配动画 + 三句价值主张（看清每个城市当下是清晨午后还是深夜 / 一眼找到全员都在工作时间的会议时段 / 常驻菜单栏随时拉出收起）。下一步选你所在的城市……"
>
> 问题：括号里那 3 条价值主张是欢迎页截图里写着的。文字描述完全是冗余。

> ✅ "按欢迎页的提示走，选一个城市作为你的本地时区。"
>
> 然后下面贴 3 张截图（欢迎页 / 城市选择 / 选中状态），让画面替代文字。

**判定标准**：如果读者**不看截图也能从文字得到全部信息**，那截图就是装饰；如果**文字也复述了截图里的细节**，那文字就是冗余。两者只能选一个 — 让截图讲细节、文字给路径。

**规则 2：动作清单用"加粗动作 + 破折号 + 效果"格式，不要用表格、不要用问句前缀。**

> ❌（用问句前缀，眼睛要扫两倍信息量）：
> > **想看明天某个时间点谁在线？** 直接拖最上方的时间滑块，所有城市卡同步切到那一刻的状态。

> ❌（用表格，看起来像参考文档，太冷）：
> | 操作 | 结果 |
> |---|---|
> | 拖滑块 | 所有城市卡同步切换状态 |

> ✅（加粗动作 + 破折号 + 效果，像快捷键备忘单一样扫）：
> - **拖滑块** — 所有城市卡同步切到那一刻的状态
> - **点左上角时间数字** — 一键跳到下一个大家都能开会的推荐时段

**规则 3：动作描述必须短（3-7 字）。**

用户会在产品里**实际尝试**这些动作。他们记不住一句话的描述，但能记住"拖滑块" "点城市名字" 这种 3-7 字的动作。看完 README 之后他们到产品里**只要记得有哪些动作，到现场一试就知道效果**。所以动作短是高优先级。

## 三、跨章节的通用原则

### 3.1 措辞：中文 README 不要直接翻译英文 UI / 营销术语

**规则**：英文 UI 术语 / 营销缩写 / IT 直译，在中文里都要换成自然中文。

| 英文原文 | ❌ 直译 | ✅ 中文自然说法 |
|---|---|---|
| chip | 芯片 | 标签 / 快捷选项 |
| CTA (call to action) | CTA | 「开始使用」按钮 / 行动按钮 |
| overlap window | 重叠窗口 | 共同时段 / 大家都能开会的时段 |
| time math | 时间数学 | 时间计算 / 时区计算 |
| city card | 城市卡 | 城市卡片 (留 "卡" OK，不要"卡片"和"卡"混用) |

**判定**：把翻译过来的中文短语放进非技术读者的对话里，他会自然这样说吗？不会就重写。

### 3.2 措辞：集体称呼词要谨慎

中文里"全队 / 团队 / 全员 / 大家"几个词的语感差别比英文里 "team / everyone / your team" 大很多。"全队"听起来像球队 / 集体，**不像同事之间的描述方式**。

> ❌ 全队定位 / 全队此刻几点 / 全员重叠窗口
> ✅ 同事所在城市 / 每位同事此刻几点 / 大家都能开会的时段

**判定**：作者会用这个词跟自己同事说话吗？

### 3.3 措辞：当一个词被指出不好，全文 grep 同义词族一次性扫干净

不要只改用户指出的那一处。"全队"被吐槽 → 也搜 "全员"、"团队"、"大家"。"芯片" 被吐槽 → 也搜 "chip"、"标签"、"快捷选项"等同类位置是否一致。

**实战教训**：Timap README 第一次"全队"被指出，AI 只改了 bullet 那处，结果用户接着指出 tagline 还有一处 — 二次往返浪费用户时间。**修一次完整扫一次**。

### 3.4 事实校验：每条产品声明都必须 grep 代码 verify

这条是最容易被忽略的纪律：
- AI 写 README 时容易凭对项目的"印象"或 sub-agent review 的总结写
- 听起来对的产品声明往往是**部分对**（功能存在但实际行为不一样）
- 读者对 README 里的产品声明**默认信任**，错误声明会建错心智模型

**实战例子**：Timap README 写了"每位同事的工作时段可独立调整" — 错的。实际代码 `setCityWorkHours` 接受**城市名**作为参数，工作时段是按**城市**设的，同一城市的所有同事共用一套。

错误来源：早期 sub-agent review 提到"每位同事的工作时间各自可调（0.5h 步进）"和"每张城市卡独立设置工作段"两个矛盾的描述糅在一句里，AI 抄进 README 时只摘了前半句，没回代码 verify。

**操作纪律**：
1. **Sub-agent review 的产品事实声明不可全信**。它们读得快但容易把矛盾的描述糅在一起。
2. **写 / 引用任何"X 可以 / 支持 / 自动 Y"声明前**，去 grep 相关 model / view / 关键词，确认现实如此。
3. **风格 sweep（jargon、用词）和事实 sweep（真假）是两件事**，要分开做两轮。
4. **作者自己几天前写过的注释 / commit message / 文档也是记忆，不可全信**。引用之前重新读当前代码 verify。

### 3.5 调性：匹配作者的实际维护态度

很多 README 模板默认包含 "贡献 / Contributing" 段或类似 PR 邀请。但**作者实际可能不期望别人来改自己代码** — 即使代码是 GPL 开源的。

skill 启动时第一件事必须问作者：**你期望别人来贡献吗？**

- 如果**不期望**：README 不写"PR 欢迎"、不写文件路径速查表、不写测试构建命令、tone 整体是"我做了个东西放这里给你用"
- 如果**期望**：才加 Contributing 段、文件路径表、构建命令、tone 调成"欢迎一起搞"

这是**根本性的 tone 决策**，会影响 README 的几乎每一节。不要默认假设"开源 = 欢迎贡献"。

### 3.6 过度承诺词要克制

> ❌ "智能算法精准定位" — "智能"、"精准"是营销词，不带任何信息
> ❌ "一秒钟搞定" — 没数据支撑就是夸大
> ❌ "强大的 X 引擎" — "强大"是空话

**规则**：每个修饰词都要带具体内容支撑，否则删掉。"算法"在简单实现上是过度包装（几行 if-judgement 求交集就别叫"算法"）。

### 3.7 避免稻草人比较

> ❌ "比 Spark 更专注于时区" — Spark 是邮件 app，本来就不是同类产品，这种比较是稻草人。

如果要做对比，**找真正的同类产品**对比，而且只在功能确实不同时才提。如果作者不确定有哪些同类，**宁可不比较**。

## 四、发布前的检查清单

在 README 公开（push 到远程仓库或发 release）前，**必须过一遍这份清单**：

### 4.1 内容核心层

- [ ] Tagline 闭眼能想出画面？
- [ ] Hero 截图捕捉了产品的"价值瞬间"？数据是合成假姓名 + 跨地理 + 状态有差异？
- [ ] "能干什么"段是否 ≤ 4 条 bullet？每条都是差异化卖点（不是基线特征）？
- [ ] 每条 bullet 是不是"用户视角"标题（不是技术名词）？
- [ ] 安装步骤在最新目标系统上实测过？
- [ ] 安装受阻的"找不到入口"兜底有写吗？

### 4.2 措辞层

- [ ] grep 全文：有没有英文 UI 直译（chip / CTA / overlap 等）？
- [ ] grep 全文：集体称呼词是否一致（不要混用全队/全员/大家）？
- [ ] grep 全文：jargon / 缩写 / 隐喻是否过多？

### 4.3 事实层

- [ ] 每条"X 可以 / 支持 / 自动 Y"的产品声明，回代码 grep 验证过？
- [ ] CLAUDE.md / 注释 / 旧 commit 引用的事实，重新读当前代码 verify 过？

### 4.4 调性层

- [ ] 跟作者确认了 maintenance / openness 态度？Contributing 段去/留对吗？
- [ ] 没有"PR 欢迎"等不匹配作者意图的邀请？

### 4.5 双语镜像（如果适用）

- [ ] 中文版定稿之后再写英文镜像，不要并行写
- [ ] 英文镜像跑一遍英文母语 reviewer，找 ChatGPT 味 / 翻译腔

## 五、附录：可复用的 sub-agent 评审 prompt 模板

为 README 写完第一稿后，跑两轮多视角 sub-agent 评审。

### 第一轮（v1 → v2）：3 个并行 reviewer

#### Reviewer A：第一次访问的潜在用户

```
你刚在 Twitter 看到有人推了 [PROJECT_NAME]。点进 GitHub README 30 秒决定要不要继续读 / 下载 / 收藏。

精读：[README path]

回答四个问题，每个 1-2 句话即可：
1. 30 秒内你 get 到这是什么产品 / 解决什么问题了吗？没的话卡在哪？
2. 你会下载 / 收藏吗？什么因素让你不会？
3. 你会推荐给同事 / 转发吗？
4. 第一屏（不滚动）前是否有让你想继续读的 hook？没有的话，第一屏需要补什么？

最后给出 1-10 分（"会不会让我留下来"），并指出最该改的一处。不超过 350 字。
```

#### Reviewer B：营销/文案专家

```
你是有 10 年经验的科技产品文案专家。审 [PROJECT_NAME] 的 [中/英] README。

精读：[README path]

从文案/营销角度评估：
1. 价值主张层次：tagline → 第一段 → 4 个 bullet。每一层都在前进还是在重复？
2. 用户自我代入：开篇是第一人称作者自述还是第二人称"你"？
3. bullet 措辞：每条同时讲到了"用户痛点 → 动作 → 收益"吗？
4. 缺失的"social proof"或"对比锚"：跟主流竞品对比有没有？
5. CTA 路径：从 README 顶部到主要 CTA — 用户被说服后到行动的路径顺不顺？

输出：
- 整体卖点表达力（1-10 分 + 一句理由）
- "开篇 tagline + 第一段"重写示范
- 4 个 bullet 的重写示范
- 1 条针对该产品上下文的特殊建议

不超过 600 字。
```

#### Reviewer C：技术贡献者 / 想 fork 的开发者

```
你熟悉 [TECH_STACK]，从 Hacker News 看到 [PROJECT_NAME]。评估这个项目值不值得 fork / contribute。

精读：[README path]
看一眼仓库结构：ls [repo root]

评估：
1. 技术栈是否清晰（30 秒内说出语言、框架、运行时、平台）
2. 架构信号：README 给的简介对技术读者来说够不够？
3. 缺失的技术信号：badges、CI 状态、版本兼容性？
4. 项目调性：hobby 还是认真维护？README 态度有没有匹配？

输出：
- 总体技术专业度印象（1-10 分 + 一句理由）
- 5 条具体改进建议
- 1 条最容易执行的"快赢"修改

不超过 450 字。
```

### 第二轮（v2 → v3）：换不同视角避免闭环

#### Reviewer D：怀疑论者

```
你是个挑剔的开源项目读者。打开 [PROJECT_NAME] 的 v2 README，**带着怀疑去读** — 找它过度吹嘘 / 自我感动 / 言过其实 / 缺乏证据 的地方。

精读：[README path]

要找：
1. 吹得过的句子（"算法"、"智能"、"一秒"等强词）— 哪些过度承诺？
2. 没证据支撑的卖点 — 哪些只是声明，没截图 / 链接 / 数据证明？
3. 表演式谦虚 — 哪些是真诚，哪些是模板？
4. 比较锚是否公平 — 是否在和稻草人对比？
5. bullet 与现实的偏差 — 描述的功能截图能验证吗？

输出：
- 整体可信度（1-10 分）
- 5 条最值得改的"过度宣传/缺乏证据"问题，每条引用原文
- 1 条"如果什么都不改、最该删的句子"
- 1 条"如果只能加一个证据点、最该加的"

不超过 500 字。
```

#### Reviewer E：母语 / 文化 tone editor

中文 README 用：
```
你是中文科技博客的资深编辑。给 [PROJECT_NAME] 中文 README v2 做 tone polish。重点：
1. 直接英译过来的生硬措辞（"芯片" 应该是 "标签" / "CTA" 应该是 "按钮"等）
2. 集体称呼词的语感（"全队 / 团队 / 全员 / 大家" 哪个最自然）
3. 中文 IT 文档里不该出现的英文 jargon
4. 长句应该断成短句的地方
5. 文化适配：举例 / 类比是否对中文读者友好

输出：5 条最值得改的措辞 + 1 段示范重写。不超过 400 字。
```

英文 README 用：
```
You're a senior tech editor specializing in open-source READMEs. Polish [PROJECT_NAME]'s English README v2 for tone.

Hunt for:
1. ChatGPT-isms ("Let me / Furthermore / In conclusion / I'd be happy to")
2. Marketing fluff ("seamlessly", "powerful", "intuitive")
3. Sentences that read like translations from another language
4. Awkward parallelisms in bullet lists
5. Anywhere the tone shifts unexpectedly

Output: top 5 specific changes + 1 paragraph rewrite. Under 400 words.
```

#### Reviewer F：功能覆盖审计 / 事实校验

```
你对 [PROJECT_NAME] 的代码非常熟悉。任务：read the README v2 + diff 它跟代码实际能做的事，找出：

1. README 没提但代码里有的优秀功能（被埋没的卖点）
2. README 提了但描述不清的（应加一行佐料）
3. README 提了但代码里没有的（事实错误！警报）
4. 截图能讲但没用上的功能（视觉素材浪费）

精读：
- README: [README path]
- 代码：[main source files]
- L10n / i18n 字符串：[L10n file]

输出：
- 功能覆盖度（1-10 分）
- Top 5 README 没提但应该提的关键功能
- 3 个 README 提了但描述太弱的地方
- 任何事实错误（即"README 写了但代码不是这样"）— 这个最严重

不超过 500 字。
```

## 六、附录：触发条件与开场流程（给 skill 用）

### Skill 触发关键词

- "写 README" / "改 README" / "review README" / "优化 README"
- "我开源了 / 我准备开源 / 准备发布到 GitHub"
- "我要写 / 改 / 优化 / 打磨 项目主页"
- "READMEs" / "readme.md"

### Skill 启动后的开场流程

skill 开场**不要直接写**。先问 4 个问题确认上下文：

1. **作者维护态度**：你期望别人来贡献代码吗？还是只是公开源码不想被打扰？
2. **目标读者**：技术读者优先，还是普通用户优先？两者通吃但侧重哪边？
3. **语言**：单语 / 双语？双语的话哪个是主语言？
4. **现有素材**：有截图吗？有 logo 吗？有前一版 README 吗？

这些回答会影响：tone、结构、是否包含 contributor 段、bullet 措辞密度、CTA 路径几乎所有决策。

### 后续迭代

写完 v1 后跑第一轮 3 个 reviewer（Reviewer A/B/C）→ 综合反馈写 v2 → 跑第二轮 3 个 reviewer（D/E/F）→ 综合反馈写 v3 → 让作者人眼审一遍 → 双语镜像（如果适用）→ 最终事实 sweep → 发布。

通常 3 轮迭代是合适的；超过 5 轮说明前面有什么没想清楚（多半是 tone 没匹配作者态度）。

## 七、附录：从 Timap 实战提炼的"反复改"模式

按"修了几次"排序，让 skill 内化哪些类型的问题是高频反复事件：

| 问题类型 | 修了几次 | 高频原因 |
|---|---|---|
| Tagline 太"产品经理腔" | 3 次 | 抽象/具象的差距很微妙，凭直觉改不过来，靠"画面感"原则才定稿 |
| 集体称呼词不自然 | 2 次 | 第一次只改用户指出的一处，没全文 sweep 同义词 |
| 安装方法在新 macOS 上不通 | 4 次 | 反复在旧系统假设上加补丁，不是测真实新系统 |
| 说错了产品事实（按城市还是按人）| 1 次但事故严重 | 抄 sub-agent review 的事实声明不 verify |
| 过度承诺词（"算法"、"一秒"）| 2 次 | 第一轮风格 reviewer 没抓到，第二轮怀疑论者才抓到 |
| Hero 截图选不对 demo 团队 | 4 次 | 每次改完作者自己看觉得不对劲但说不清，最终明确出"绿色 band 必须居中、足够长"准则 |

**模式总结**（让 skill 内化）：
- 反复修的问题往往是**作者在自己机器上无法 verify** 的（新系统行为、用户视觉习惯、跨语言措辞）
- 单轮 review 抓不到的问题需要**多轮多视角**才能浮出
- 事实错误一次写错就难发现，所以**事实 sweep 必须独立做一轮**
- 视觉素材（hero 截图）的迭代往往比文字迭代多 — 因为画面对不对要看到实际渲染才知道

skill 内化这些模式之后，第一次写 README 就能避开大多数坑，把迭代轮次从 7-8 轮压到 3 轮。
